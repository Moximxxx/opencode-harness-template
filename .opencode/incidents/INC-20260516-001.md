## 现象

validate-contract.sh 在合同验证阶段对 `files_to_modify` 中的文件执行存在性检查。当合同目标为**新建文件**时（如 DOCS-001 的 README.md 和 .gitignore），由于文件尚未创建，触发了如下误报：

```
RESULT: BLOCK 合同校验失败: DOCS-001
  1. /files_to_modify/README.md: 文件不存在: README.md
  2. /files_to_modify/.gitignore: 文件不存在: .gitignore
```

该 BLOCK 阻止了 validate-contract 钩子通过，需要人工介入绕过。

---

## 根因

`validate-contract.sh` 第 65-74 行的文件存在性检查逻辑：

```javascript
// 自定义校验: 文件存在性
if (Array.isArray(contract.files_to_modify)) {
    contract.files_to_modify.forEach(function(f) {
        if (!fs.existsSync(path.join(projectRoot, f))) {
            errors.push('/files_to_modify/' + f + ': 文件不存在: ' + f);
        }
    });
}
```

该逻辑未区分**修改已有文件**和**创建新文件**两种场景。对于修改场景，文件存在性检查是有意义的（防止误修改不存在的文件）；对于新建场景，文件不存在是正常预期。

---

## 影响

- 所有 `files_to_modify` 包含新建文件的任务在合同验证阶段被误拦
- 文档类（DOCS）任务尤为突出，因其 files_to_modify 通常全部为新建文件
- 需要 Coordinator 手动绕过或忽略该误报，降低自动化程度

---

## 修复方案

### 方案 A（推荐）: 将文件存在性检查移至后置钩子

将文件存在性检查从 `validate-contract.sh`（前置验证）移至 `post-edit-verify.sh`（后置验证）。

**优势**: 
- 前置验证关注合同结构完整性（Schema + 时效性）
- 后置验证关注执行结果（文件确实被创建/修改）
- 逻辑干净，各司其职

**修改**: 
1. 从 `validate-contract.sh` 移除第 65-74 行
2. 在 `post-edit-verify.sh`（待实现）中增加文件存在性检查，区分新建/修改场景

### 方案 B: 增加 `--allow-new-files` 标志

在 `validate-contract.sh` 中增加可选标志，允许合同显式声明某文件为新建：

```json
{
  "files_to_modify": ["README.md"],
  "new_files": ["README.md"]
}
```

**劣势**: 增加合同字段复杂度。
